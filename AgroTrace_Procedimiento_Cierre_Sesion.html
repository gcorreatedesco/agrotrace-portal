Cierre y Retoma de Sesión

Procedimiento para sesiones de vibe-coding con Claude

Documento
v1.0
AgroTrace · 2026
Una sesión larga de vibe-coding acumula contexto valioso: decisiones tomadas, código producido, problemas resueltos, ramas sin terminar. Si no se captura al final, la próxima sesión empieza a ciegas y se gasta buena parte del tiempo reconstruyendo lo que ya estaba claro.

Este procedimiento toma 5-10 minutos al cerrar y ahorra 20-30 al retomar. Hacerlo como último acto de cada sesión productiva.
Cuándo activar el procedimiento
Señales de que es momento de cerrar
  • Claude empieza a repetir cosas ya discutidas o "olvida" decisiones tomadas
  • Las respuestas se vuelven más genéricas o menos precisas que al inicio
  • La sesión lleva más de 90 minutos activos
  • Se terminó una funcionalidad importante y hay una pausa natural
  • Aparece el aviso de contexto comprimido en la sesión
También hacerlo aunque la sesión esté "fresca"
  • Al terminar el día aunque haya sido una sesión corta
  • Antes de una pausa de más de 24 horas
  • Después de implementar un módulo completo
  • Cuando se tomaron decisiones de arquitectura importantes
  • Si hubo cambios en la base de datos (schema, RLS, migraciones)
Procedimiento de cierre — paso a paso
1
Pedirle el resumen a Claude
Copiar y pegar este prompt al final de la sesión
Usá este prompt exacto. Está diseñado para extraer todo lo relevante sin ambigüedad. Claude tiene el contexto completo de la sesión en memoria en ese momento — es el mejor momento para pedirlo.
Prompt de cierre — copiar tal cual
Antes de cerrar la sesión, necesito que hagas un resumen estructurado para poder retomar sin perder contexto. Incluí:

1. QUÉ CONSTRUIMOS HOY — lista de funcionalidades o cambios implementados, con una línea de descripción cada uno. Si hay código guardado en archivos, mencioná los archivos afectados.

2. DECISIONES TOMADAS — decisiones de diseño, arquitectura o negocio que se tomaron durante la sesión y por qué (aunque parezcan obvias, anotarlas evita volver a discutirlas).

3. ESTADO ACTUAL — para cada módulo o área del sistema: qué está completo, qué está en progreso, qué está pendiente.

4. PROBLEMAS O BUGS ENCONTRADOS — si quedó algo sin resolver o con una solución provisoria, documentarlo.

5. PRÓXIMOS PASOS — lista ordenada por prioridad de lo que queda por hacer, con suficiente detalle para retomar sin preguntar.

6. COMANDOS O CONFIGURACIONES A RECORDAR — cualquier comando de terminal, SQL, configuración de servicio externo, o URL relevante que se usó hoy.

Formatealo en Markdown limpio para guardarlo en summary.md.
Tip: Si la sesión fue muy larga y Claude ya tiene contexto comprimido, el resumen puede estar incompleto. En ese caso, scrolleá hacia arriba en la conversación y agregá manualmente lo que falta en el paso siguiente.
2
Revisar y completar el resumen
El resumen de Claude es un borrador — revisarlo antes de guardar
Chequeá que el resumen generado contenga todo lo relevante. Esta lista ayuda a detectar lo que Claude puede haber omitido.
  • ¿Están todos los archivos modificados? (no solo los nuevos, también los editados)
  • ¿Las decisiones de negocio tienen el "por qué"? (no solo el "qué")
  • ¿Quedó algún workaround o solución temporal sin documentar?
  • ¿Hay migraciones SQL que se ejecutaron en Supabase que no están en el schema?
  • ¿Los próximos pasos son suficientemente concretos para retomar sin preguntar?
  • ¿Hay algún servicio externo (Supabase, Resend, GitHub) con configuración que cambió?
  • ¿Quedó algo "a medio hacer" que puede romper algo si se toca sin saber el contexto?
Atención: Si quedó código incompleto o con TODOs, marcarlo explícitamente en el resumen. "Función X está comentada hasta que se resuelva Y" es información crítica que evita horas de debug en la próxima sesión.
3
Guardar los archivos de contexto
Dos archivos a actualizar antes de cerrar
El repositorio tiene dos archivos de contexto que deben mantenerse actualizados. Claude puede escribirlos directamente si se le pide.
Archivo Qué contiene Cuándo actualizar
summary.md Resumen acumulativo de todo lo construido. Siempre se sobreescribe con la versión más completa y actualizada. Al final de cada sesión productiva
Proximospasos.md Lista ordenada de próximos pasos con suficiente detalle para retomar. Refleja el estado real, no aspiracional. Cada vez que cambia la prioridad o se completan ítems
Prompt para que Claude actualice los archivos
Con el resumen que acabas de generar, actualizá los dos archivos de contexto del repositorio:

1. Sobreescribí summary.md con el resumen completo en formato Markdown.
2. Actualizá Proximospasos.md con los próximos pasos en orden de prioridad, con suficiente detalle para retomar sin preguntas. Eliminá los ítems ya completados.

Después hacé git add y git commit con mensaje "docs: actualizar resumen y próximos pasos — [fecha de hoy]".
Nota sobre la memoria automática: Claude Code guarda memorias en ~/.claude/projects/.../memory/. Estas persisten entre sesiones y complementan los archivos del repo. Si tomaste una decisión importante de diseño o preferencia de trabajo, pedile a Claude que la guarde en memoria: "recordá que decidimos X porque Y".
4
Commit y push
Dejar el repositorio limpio antes de cerrar
Nunca cerrar una sesión con cambios sin commitear. Un cambio sin commit es trabajo perdido si algo falla. El push a main también actualiza GitHub Pages automáticamente.
  • git status — confirmar qué archivos cambiaron
  • Revisar que no haya archivos de credenciales o .env en el staging area
  • git add de los archivos modificados (específicos, no git add . a ciegas)
  • git commit con mensaje descriptivo
  • git push a main
  • Verificar en GitHub Pages que el deploy esté OK (1-2 minutos)
Regla: Si hay cambios que deliberadamente no se quieren commitear todavía (trabajo en progreso, experimento), dejar un comentario en el código con // WIP: [descripción] y mencionarlo en el resumen. No dejar cambios "flotando" sin documentar.
5
Verificar que todo funciona
30 segundos que evitan arrancar la próxima sesión debuggeando
Abrir la URL de producción y hacer un smoke test rápido de lo que se modificó hoy.
  • Abrir GitHub Pages y verificar que carga sin errores
  • Abrir la consola del navegador (F12) — no debería haber errores en rojo
  • Probar la funcionalidad principal que se modificó hoy
  • Si se modificó algo de Supabase: verificar que las queries siguen funcionando
Procedimiento de retoma — inicio de sesión
Al abrir una nueva sesión, Claude arranca sin contexto de la anterior. El objetivo es dárselo de forma eficiente en un solo mensaje, no en varias idas y vueltas.
1Abrir Claude Code en el proyecto
→
2Enviar el prompt de retoma
→
3Claude lee los archivos y toma contexto
→
4Confirmar entendimiento y arrancar
Prompt de retoma — copiar al inicio de la nueva sesión
Retomamos el proyecto AgroTrace. Antes de arrancar, leé estos archivos para tomar contexto:
- summary.md → qué está construido y cómo funciona
- Proximospasos.md → qué sigue y en qué orden
- CLAUDE.md → reglas del proyecto, stack y convenciones

Cuando los hayas leído, confirmame en 3-4 líneas qué entendés que es el estado actual y cuál sería el primer paso lógico para hoy. Yo te confirmo o corrijo antes de arrancar.
Por qué pedir confirmación: Claude puede leer los archivos pero interpretarlos distinto a lo que vos tenés en mente. Ese intercambio de 2 mensajes al inicio alinea el entendimiento y evita que Claude arranque implementando algo en la dirección equivocada.
Referencia rápida — archivos de contexto del proyecto
Archivo Propósito Quién lo lee Frecuencia de update
CLAUDE.md Reglas fijas del proyecto: stack, paleta, convenciones, arquitectura. No cambia frecuentemente. Claude (automático) Solo cuando cambia el stack o las convenciones

Errores comunes a evitar
Anti-patrón Por qué es un problema Qué hacer en cambio
Arrancar la sesión nueva sin prompt de retoma Claude no tiene contexto — empieza genérico y hace preguntas básicas que ya tienen respuesta Siempre enviar el prompt de retoma como primer mensaje
Pedirle a Claude que "recuerde" algo sin guardarlo en un archivo La memoria de sesión no persiste. Al cerrar la pestaña, se pierde. Todo lo importante va a summary.md, Proximospasos.md o memory/
Hacer muchos cambios sin commitear y cerrar Si el browser crashea o se cierra sin guardar, el trabajo se pierde Commit al terminar cada funcionalidad, no al final del día
Continuar una sesión que ya está muy degradada Claude empieza a contradecirse o a ignorar restricciones ya establecidas Detectar las señales de la tabla anterior y cerrar antes de que empeore
Resumen demasiado largo y narrativo Claude tarda más en procesarlo y pierde los puntos clave en el ruido Listas cortas, puntos concretos, sin prosa innecesaria
Sobre el contexto comprimido: Claude Code comprime automáticamente conversaciones largas para no exceder el límite de contexto. Cuando eso pasa, el historial detallado desaparece pero los archivos del repo siguen disponibles. Por eso los archivos de contexto son más confiables que "lo que Claude recuerda de la sesión".
