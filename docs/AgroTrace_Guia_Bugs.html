Concurrencia y Estado

Las 8 categorías de errores encontrados en las auditorías de agosto 2026 — explicadas en lenguaje claro, con ejemplos reales del código.

Auditorías: 2026-08-04 y 2026-08-24 · actualizada septiembre 2026

¿Qué es una auditoría de concurrencia?

En un sistema web, muchas cosas pueden pasar al mismo tiempo: dos clicks seguidos en el mismo botón, dos personas usando la app, una operación que tarda y el usuario que no espera. Los bugs de concurrencia son los que aparecen en esos momentos — no cuando todo va bien, sino cuando el tiempo importa.

Los bugs de sincronización de estado son los primos cercanos: ocurren cuando el programa "recuerda" algo que ya no es verdad. Usás un dato viejo sin saber que cambió.

Esta guía clasifica los bugs encontrados en AgroTrace (auditorías de agosto 2026) en 8 categorías. Para cada una: qué es, por qué ocurre, cómo se veía antes y cómo quedó después de la corrección.

A
Doble submit
Race condition · Double-submit · Missing guard flag
● Severidad Alta — corrupción de datos
En palabras simples

Apretás "Guardar" y la pantalla no responde inmediatamente porque está esperando respuesta del servidor. Lo apretás de nuevo. El formulario se envía dos veces. Resultado: dos registros idénticos en la base de datos, o el stock descontado dos veces.

Por qué ocurre en AgroTrace

Las funciones que guardan datos necesitan comunicarse con Supabase, lo que lleva tiempo (entre 200ms y 2 segundos). Ese tiempo entre que apretás el botón y que la pantalla confirma es la ventana de riesgo. Si el botón sigue activo durante esa espera, un segundo click lanza una segunda ejecución en paralelo.

Cómo se veía antes

Antes — sin protección
async function guardarEntrega() {
  // El botón sigue activo. Si el usuario hace click dos veces,
  // esta función corre dos veces en paralelo.
  const res = await sb.from('entregas').insert({ ... })
  await sb.from('flores_cosechadas').update({ stock: nuevoStock })
}
Después — con guard flag
let _guardandoEntrega = false;

async function guardarEntrega() {
  if (_guardandoEntrega) return; // segundo click → sale inmediatamente
  _guardandoEntrega = true;
  try {
    const res = await sb.from('entregas').insert({ ... })
    await sb.from('flores_cosechadas').update({ stock: nuevoStock })
  } finally {
    _guardandoEntrega = false; // siempre se libera, incluso si hay error
  }
}

Para botones visibles, la variante es deshabilitar el botón (mejor experiencia de usuario): btn.disabled = true antes del primer await, y btn.disabled = false en el bloque finally.

B
Stale state — datos desactualizados
Stale cache · Stale closure · TOCTOU (Time-of-Check vs Time-of-Use)
● Severidad Alta — stock incorrecto, datos de lote erróneo
En palabras simples

Anotás el stock disponible en un papelito cuando abrís el formulario. Cinco minutos después, otro usuario ya usó parte de ese stock. Vos seguís calculando con el número del papelito. El resultado: el stock queda negativo o incorrecto.

Variante B-1: caché obsoleto (Stale cache)

En AgroTrace, cuando abrís un lote, los datos se cargan en la variable global HIST_DATA. Funciones como guardarEntrega() usaban ese número para calcular cuánto descontar del stock. Pero si pasó tiempo desde que abriste el lote, ese número puede estar desactualizado.

Antes — usando el caché
// Stock leído al abrir el lote, hace minutos
const stockActual = HIST_DATA.flores?.stock_actual ?? 0;
const nuevoStock = stockActual - cantidadEntregada;
await sb.from('flores_cosechadas').update({ stock_actual: nuevoStock })
Después — lectura fresca antes de usar
// Leer el stock real justo antes de modificarlo
const { data: flores } = await sb
  .from('flores_cosechadas')
  .select('stock_actual')
  .eq('id', floresId)
  .single();
const nuevoStock = flores.stock_actual - cantidadEntregada;
await sb.from('flores_cosechadas').update({ stock_actual: nuevoStock })

Variante B-2: closure obsoleto (Stale closure)

La función openLote(id) hace varias consultas en paralelo. Si el usuario, mientras espera, hace click en otro lote, la variable LOTE_ACTIVO ya apunta al nuevo lote. Pero el código del lote anterior sigue corriendo y al terminar pisa los datos del nuevo.

Después — verificar que el contexto no cambió
async function openLote(id) {
  const capturedId = id; // guardar el ID antes de cualquier await
  const [loteData, histData] = await Promise.all([...]);
  // Verificar que el usuario no navegó a otro lote mientras esperábamos
  if (LOTE_ACTIVO?.id !== capturedId) return;
  // Recién acá es seguro usar los datos
  HIST_DATA = histData;
}

C
Constraint de unicidad faltante
Missing unique constraint · DB-level integrity
● Severidad Media — duplicados en base de datos
En palabras simples

Si dos personas intentan registrar el mismo paciente al mismo tiempo, el código de validación en JavaScript puede no alcanzar a detectar que ya existe — ambas consultas llegan a la base de datos antes de que ninguna vea la otra. La base de datos, sin una regla explícita, acepta los dos registros.

Por qué la validación en JavaScript no alcanza

El código hace primero una consulta de verificación ("¿ya existe este paciente?") y luego el insert. Entre esas dos operaciones, otra ejecución puede insertar el mismo registro. Este problema se llama TOCTOU: Time Of Check vs Time Of Use. La única solución real está en la base de datos.

Fix — constraint a nivel de base de datos
-- Ejecutar en Supabase SQL Editor
ALTER TABLE public.pacientes
  ADD CONSTRAINT pacientes_usuario_numero_unique
  UNIQUE (usuario_id, numero);

Con este constraint, si dos inserts idénticos llegan al mismo tiempo, la base de datos rechaza el segundo con un error claro. El código JavaScript puede capturar ese error y mostrar un mensaje al usuario.

Estado
pacientes (usuario_id, numero) — constraint ya existía ✓
D
Transacción incompleta
Non-atomic multi-step operation · Compensating transaction · Orphaned record
● Severidad Alta — datos huérfanos, inconsistencia de stock
En palabras simples

Registrar una entrega son dos pasos: (1) guardar la entrega, (2) actualizar el stock disponible. Si el paso 1 funciona pero el paso 2 falla por un error de conexión, quedás con una entrega registrada pero el stock sin descontar. Los números no cierran.

El problema de fondo: no hay transacciones reales

En bases de datos relacionales existe el concepto de transacción atómica: un conjunto de operaciones que se ejecutan todas juntas o ninguna. Si el cliente de Supabase en JavaScript lo soportara, el fix sería simple. Pero desde el frontend, no hay esa garantía.

La solución práctica es la transacción compensatoria: si el segundo paso falla, deshacés el primero manualmente con un DELETE.

Antes — sin compensación
await sb.from('entregas').insert({ cantidad, flores_id })
// Si esto falla, la entrega quedó registrada pero el stock no se movió
await sb.from('flores_cosechadas').update({ stock_actual: nuevoStock })
Después — con transacción compensatoria
// Paso 1: insertar y capturar el ID del nuevo registro
const { data: entrega } = await serverWrite('entregas', { cantidad, flores_id });
const entregaId = entrega.id;

// Paso 2: actualizar stock. Si falla, deshacemos el paso 1.
try {
  await serverWrite('flores_cosechadas', { stock_actual: nuevoStock }, 'update', filtro);
} catch (e) {
  // Rollback: borrar la entrega recién creada
  await sb.from('entregas').delete().eq('id', entregaId);
  throw e; // propagar el error para que el usuario lo vea
}

E
Contaminación entre organizaciones
Tenant context leak · Stale global state · Cross-tenant data bleed
● Severidad Media — datos de ONG A visibles mientras se navega ONG B
En palabras simples

El Responsable Técnico abre el portal de la Asociación "Verde". Ve sus lotes. Cierra y abre el portal de la Asociación "Horizonte". Durante un segundo, el sistema podría seguir mostrando los lotes de "Verde" mientras carga los de "Horizonte". Si hay un error de timing, podría guardar datos de Horizonte con el contexto de Verde.

Por qué ocurre

El portal es una Single Page Application (SPA): una sola página que no se recarga entre una ONG y otra. Las variables globales (LOTE_ACTIVO, HIST_DATA, PAC_DATA, etc.) persisten en memoria. Si no se resetean explícitamente cuando cambia el contexto de ONG, mezclan datos de dos organizaciones distintas.

Antes — sin reset explícito
async function initApp() {
  // Variables globales con valores de la sesión anterior
  await Promise.all([cargarLotes(), cargarMaterial()]);
}
Después — reset antes de cargar
async function initApp() {
  // Reset completo antes de cualquier consulta a la DB
  LOTE_ACTIVO = null;
  HIST_DATA = {};
  INCONSISTENCIAS = {};
  MAT_ACTIVO = null;
  MAT_TIPO = null;
  PAC_DATA = [];
  PAC_EDIT_ID = null;
  ESTABL_EDITANDO = null;

  // Recién ahora cargar los datos de la ONG correcta
  await Promise.all([cargarLotes(), cargarMaterial()]);
}

F
Fire-and-forget
Unhandled promise rejection · Missing error handler on async side effects
● Severidad Baja — errores silenciosos en logging
En palabras simples

Mandás una carta sin acuse de recibo. Si llega, bien. Si no llega, nunca lo sabés. En código: llamás a una función asíncrona pero no esperás su resultado ni te preparás para el caso de que falle.

Por qué es un problema

En JavaScript, una promesa que falla sin que nadie la "atrape" genera un Unhandled Promise Rejection. Dependiendo del navegador y la versión, esto puede:

  • Mostrar un error en la consola (siempre)
  • En versiones antiguas: cortar la ejecución del código que sigue
  • En futuras versiones: terminar el proceso (como ocurre en Node.js)

En AgroTrace, logActividad() (que registra el historial de acciones) era llamada sin manejo de error. Si Supabase tenía un problema momentáneo, el log fallaba y podía interrumpir la operación principal.

Antes — sin manejo
logActividad('avanzar_etapa', { lote_id: id, etapa: nuevaEtapa })
// Si logActividad lanza un error, nadie lo captura
Después — error silenciado intencionalmente
logActividad('avanzar_etapa', { lote_id: id, etapa: nuevaEtapa })
  .catch(() => {}); // el log no es crítico — si falla, se ignora

El .catch(()=>{}) vacío es intencional: dice explícitamente "si esto falla, no me importa". Es diferente a ignorarlo sin querer.

G
RLS incorrecto
Row Level Security misconfiguration · Policy logic error · Wrong column reference
● Severidad SQL — acceso bloqueado o habilitado incorrectamente
En palabras simples

Las políticas RLS son las reglas de seguridad de la base de datos: quién puede leer, escribir o modificar cada tabla. Si están mal configuradas, puede pasar lo contrario de lo esperado: un usuario no puede hacer algo que debería poder hacer, o puede hacer algo que no debería.

Variante G-1: FOR ALL con subquery EXISTS

En Supabase/PostgREST existe una trampa sutil: una política que dice FOR ALL USING (EXISTS(...)) aplica la condición correctamente para lectura (SELECT), actualización (UPDATE) y borrado (DELETE), pero no para inserción (INSERT). Los inserts pasan o fallan de manera impredecible.

Antes — patrón incorrecto para INSERT
-- Esta política falla silenciosamente en INSERTs
CREATE POLICY "organizaciones_access" ON public.organizaciones
  FOR ALL USING (EXISTS (
    SELECT 1 FROM rt_organizaciones ro
    WHERE ro.rt_id = auth.uid()
  ));
Después — políticas separadas por operación
CREATE POLICY "organizaciones_select" ON public.organizaciones
  FOR SELECT USING (condicion);

CREATE POLICY "organizaciones_insert" ON public.organizaciones
  FOR INSERT WITH CHECK (condicion);

CREATE POLICY "organizaciones_update" ON public.organizaciones
  FOR UPDATE USING (condicion);

Variante G-2: nombres de columna incorrectos

Una política SQL que referencia una columna que no existe falla en tiempo de ejecución con un error críptico. En la auditoría, el SQL usaba ro.rt_usuario_id y ro.organizacion_id cuando los nombres reales en la tabla son rt_id y ong_id.

El síntoma: ERROR: 42703: column ro.rt_usuario_id does not exist. Siempre verificar los nombres exactos de columnas contra el archivo supabase_schema.sql antes de escribir políticas RLS.

H
Inactividad de botones por guardado incompleto
Silent no-op save · Missing INSERT branch · False success alert
● Severidad Media — el botón "no hace nada" (con un caso de corrupción en H-3)
En palabras simples

Apretás "Guardar", la pantalla no protesta, pero cuando volvés a mirar, nada se guardó. Y a veces aparece un cartel de "Guardado correctamente" aunque en realidad no se escribió nada. El botón parece funcionar, pero es una fachada.

Por qué ocurre en AgroTrace

Los paneles de etapas (Nursery, Vegetativa, Floración…) comparten funciones de guardado que deciden entre actualizar un registro existente o crear uno nuevo. Cuando esa lógica tiene un hueco — falta la rama de creación, o confunde "hay un objeto en memoria" con "hay un registro en la base" — el guardado corre pero no persiste. Apareció sobre todo en sublotes, que a menudo todavía no tienen registro propio de etapa. Esta categoría se sumó en la auditoría del 2026-08-24.

H-1 · Rama UPDATE sin rama INSERT

La función tiene if(d?.id){ UPDATE } pero le falta el else { INSERT }. Si el registro aún no existe (lote nuevo, sublote, primer guardado de una etapa), el botón corre pero no escribe nada.

Antes — solo actualiza
const d = HIST_DATA.nursery;
if (d?.id) {
  await sb.from('etapa_nursery').update({ ... }).eq('id', d.id);
}
// Si es un sublote sin etapa_nursery propia, no pasa NADA
Después — actualiza o inserta
if (d?.id) {
  await sb.from('etapa_nursery').update({ ... }).eq('id', d.id);
} else {
  // El sublote no tenía registro: crearlo derivando datos del lote
  await sb.from('etapa_nursery').insert({
    lote_id: LOTE_ACTIVO.id,
    fecha_inicio: LOTE_ACTIVO.fechaInicioRaw,
    origen_material: origenDerivado, ...
  });
}

H-2 · Alert falso de éxito

El alert('Guardado correctamente.') del final aparece aunque ninguna rama haya ejecutado una operación real en la base. Se resuelve con una bandera savedOk que solo se enciende dentro de una rama que sí escribe.

Después — no declarar éxito sin escribir
let savedOk = false;
if (d?.id)         { savedOk = true; ({error} = await sb.from(...).update(...)); }
else if (fi && ci) { savedOk = true; ({error} = await sb.from(...).insert(...)); }
if (!savedOk) return;              // ninguna rama guardó → no mentir
if (error) { alert('Error: ' + error.message); return; }
alert('Guardado correctamente.');  // solo si de verdad se guardó

H-3 · if(d) en vez de if(d?.id) — el UUID "undefined"

● Este sub-caso es Severidad Alta — la query falla o corrompe

Cuando HIST_DATA se pre-llena con un objeto por defecto sin id (por ejemplo { cantidad_ingreso: 30 }), la condición if(d) da verdadero igual. El código entra a la rama UPDATE con d.id === undefined, y Supabase recibe el UUID literal 'undefined' → error de tipo o escritura en el registro equivocado.

Antes — truthiness engañosa
if (d) {                       // entra aunque d.id sea undefined
  await sb.from('etapa_vegetativa').update({...}).eq('id', d.id);
  // d.id = undefined → Supabase recibe el UUID 'undefined'
}
Después — exigir id real
if (d?.id) { /* UPDATE */ }
else      { /* INSERT */ }

H-4 · Clave null en el estado global

Usar una variable como clave de objeto sin verificar que no sea null: HIST_DATA[divKey] = {...} cuando divKey puede ser null crea la entrada basura HIST_DATA['null']. En AgroTrace, etapa_origen_division es null para sublotes creados desde Nursery.

Después — guard explícito
if (divKey && condicion) {     // no crear HIST_DATA['null']
  HIST_DATA[divKey] = { ... };
}

Para el futuro

Estos bugs no son errores de lógica de negocio — son patrones estructurales que van a reaparecer en cada función nueva que toque la base de datos. Lo más útil no es recordar los bugs específicos, sino internalizar los patrones:

  • Toda función que guarda datos necesita un guard flag
  • Nunca usar un valor cacheado para calcular un UPDATE de stock — siempre leer fresco
  • Si una operación tiene 2 pasos en DB, el primero necesita poder deshacerse
  • Al cambiar de ONG, resetear todos los globals
  • El logging nunca debe poder romper el flujo principal
  • Toda función de guardado necesita rama INSERT y rama UPDATE, y no debe declarar éxito si no persistió nada

Hallazgos posteriores (septiembre 2026)

Bugs corregidos después de las auditorías — no todos de concurrencia, pero del mismo espíritu: errores silenciosos y datos que no reflejan la última versión.

  • Cartel de validación siempre visible — la clase CSS .error-msg nunca se definió, así que el mensaje "Completá la fecha de análisis" quedaba fijo como texto plano bajo el formulario. Fix: definir la regla (oculta por defecto, visible al fallar).
  • Reporte REPROCANN tomaba un análisis arbitrario — one(flores.analisis_calidad) devolvía el primer elemento sin ordenar. Con varios análisis por lote podía mostrar uno viejo. Fix: ordenar por creado_en (orden real de carga) y tomar el último; las correcciones se reflejan porque hacen UPDATE in situ.
  • ReferenceError silencioso en crearSublote — const usado antes de declararse (temporal dead zone). Mismo síntoma que la categoría H (botón inactivo sin feedback). Fix: mover la declaración al inicio del try.
